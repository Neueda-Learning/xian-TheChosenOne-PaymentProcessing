# 支付处理系统训练项目

[TOC]

## 概述

你们的团队需要设计一个支付处理应用程序，用于处理金融支付的完整生命周期。

该系统将从支付创建开始，经过校验、处理，直到完成（或失败），并维护状态变更的完整审计轨迹。

你们的任务是构建这个应用。

## 技术目标

你们应以创建一个支付处理 REST API 为目标。这将是你们学习 API 的训练周中的主要任务。

该 API 应支持在支付完整生命周期内的创建、查询和追踪。

当你们在核心需求上取得进展后，将提供进一步增强的需求。这些增强将包含开放式内容，你们可以发挥自身的技能和经验。

在开始学习 Web 前端的那一周，我们会继续推进这个项目。

对于前端部分，你们可以使用培训中学到的技术。如果想使用特定框架或其他技术，请先与讲师确认。

前端应按优先级帮助用户完成以下操作：

* 创建新支付
* 查看支付状态和详情
* 查看支付历史（所有状态迁移）
* 按状态搜索/筛选支付
* 查看失败支付的错误详情

关于详细需求，你们的讲师会扮演客户并告知他们想要的内容。你们可按需与讲师安排会议。

## 支付生命周期

系统应实现以下支付流程：

```
CREATED → VALIDATED → SENT → COMPLETED
                  ↓
              FAILED (can occur at any stage)
```

**状态定义：**

* **CREATED** - 支付已提交，但尚未校验
* **VALIDATED** - 支付已通过全部校验规则，准备发送
* **SENT** - 支付已传输到目标系统
* **COMPLETED** - 支付已成功处理并确认
* **FAILED** - 支付在流程某个阶段失败（带错误码）

## 核心需求

### API 端点

请自行设计 REST API 接口：确定哪些操作、路由和 HTTP 方法最适合用于支付的创建、查询与生命周期追踪。使用课堂所学的 REST API 技术（如 Spring Boot、Flask、Express.js 等）。

## 注意事项

1. 不需要认证，并假设只有单一用户，即无需管理用户或账户归属。

2. 持久化存储应使用你们在培训中使用过的数据库技术。

3. 充分使用 git。尽可能使用分支和 Pull Request。

4. 提供 REST API 使用文档会很有帮助。如果你们培训中学过，可考虑 Swagger/OpenAPI。

5. 对于本训练项目，不需要接入真实支付网络或网关——在系统内部模拟处理即可。

## 项目管理启动清单

1. 团队共同决定工作方式。例如：2 人做后端、1 人做 UI 设计；或在基础系统可运行前全部先做后端。

2. 制定任务清单。建议使用 Trello 等工具跟踪任务。

3. 团队中的一部分人可负责设计功能更完整的应用，另一部分人可先构建一些小功能作为演示。

4. 优先选择实现最小可用版本（MINIMAL implementation）所需的任务。

5. 讲师会定期了解你们的进展。请提前记录问题，便于当面请教。

6. 团队应共同决定初始存储的数据集合。好的团队决策有助于成功，但请记住保持敏捷（STAY AGILE）。
最大的常见问题是：一开始就采用了过于复杂的数据模型。

## 成功建议

1. 从小做起。先让系统能以最小字段存储一个非常简单的支付，然后再增强为更复杂的数据模型。

2. 尝试结对编程，通常非常有效。

3. 有意识地保持团队积极氛围。例如给团队起名、系统化安排彼此的定期 check-in。

4. 重质不重量。

5. 尽早考虑幂等性——如果有人把同一笔支付提交两次会怎样？

6. 考虑如何处理状态迁移——支付能否从 COMPLETED 回到 CREATED？（大概率不行）



## 设计考量

### 幂等性
* 如果客户端把同一笔支付提交两次会怎样？
* 应拒绝重复支付请求，还是返回已存在的支付？
* 你们如何检测重复？（可考虑使用客户端提供的幂等键）

### 重试处理
* 网络调用可能失败——你们如何处理重试？
* 状态更新是否应支持重试？
* 重试多少次后应标记为 FAILED？

### 状态迁移
* 定义合法的状态迁移（例如，COMPLETED → SENT 是不合法的）
* 实现校验以防止非法迁移
* 可考虑使用状态机模式

### 故障场景下的 API 设计
* 如何向客户端传达错误？
* 不同错误类型应返回哪些 HTTP 状态码？
* 是否应返回客户端可编程处理的错误码？

### 审计轨迹
* 每次状态变更都应记录时间戳
* 状态变更是由谁/什么触发的？
* 这对调试和合规至关重要

## 附录 B：错误码示例

系统应为不同失败场景定义清晰的错误码：

| 错误码 | 描述 | HTTP 状态 |
|------------|-------------|-------------|
| VALIDATION_FAILED | 支付未通过校验检查 | 400 |
| INSUFFICIENT_FUNDS | 源账户余额不足 | 400 |
| INVALID_ACCOUNT | 账号无效或不存在 | 400 |
| INVALID_CURRENCY | 不支持该货币代码 | 400 |
| INVALID_AMOUNT | 金额为零、负数或无效 | 400 |
| DUPLICATE_PAYMENT | 存在相同幂等键的支付 | 409 |
| INVALID_STATUS_TRANSITION | 不能从当前状态迁移到请求状态 | 400 |
| PAYMENT_NOT_FOUND | 支付 ID 不存在 | 404 |
| PROCESSING_ERROR | 支付处理期间发生内部错误 | 500 |
| NETWORK_ERROR | 与支付网络通信失败 | 503 |

## 附录 C：校验规则示例

可考虑实现如下校验规则：

1. **金额校验**
   - 金额必须大于 0
   - 金额不能超过最大限制（例如 1,000,000）
   - 对大多数货币，金额最多保留 2 位小数

2. **账户校验**
   - 源账户和目标账户必须不同
   - 账号格式必须有效
   - 账户必须在系统中存在

3. **货币校验**
   - 货币代码必须符合 ISO 4217（如 USD、EUR、GBP）
   - 系统必须支持指定货币

4. **状态迁移校验**
   - 合法迁移：
     - CREATED → VALIDATED
     - CREATED → FAILED
     - VALIDATED → SENT
     - VALIDATED → FAILED
     - SENT → COMPLETED
     - SENT → FAILED
   - 非法迁移应被拒绝，并返回清晰错误信息

## 附录 D：UI 想法

以下是一些可供参考的 UI 概念。你们**绝对不需要**完全按图实现。它们**仅用于演示**可能展示的类型。

### 创建支付页面
* 表单字段：
  - 源账户（下拉或文本输入）
  - 目标账户（文本输入）
  - 金额（数字输入）
  - 货币（下拉：USD、EUR、GBP 等）
  - 参考/描述（可选文本）
* 提交按钮
* 清晰的校验错误提示

### 支付详情页面
* 展示支付信息：
  - 支付 ID
  - 状态（颜色区分：COMPLETED 为绿色，处理中为黄色，FAILED 为红色）
  - 金额与货币
  - 账户详情
  - 时间戳
* 状态历史时间线（展示所有状态迁移）
* 若失败，展示错误码和描述

### 支付列表页面
* 支付表格或列表
* 列：支付 ID、金额、货币、状态、创建日期
* 按状态筛选（下拉或标签）
* 按支付 ID 或参考信息搜索
* 点击行查看详情

### 状态历史可视化
* 时间线视图展示：
  - 每个状态及对应时间戳
  - 支付在每个状态停留的时长
  - 备注或错误信息
  - 状态迁移的可视化标记

## 附录 E：高级功能（如果有时间）

当核心系统可用后，可考虑以下增强：

1. **批量支付**
   - 一次提交多笔支付
   - 跟踪批次状态
   - 生成批次汇总报告

2. **支付调度**
   - 安排未来执行的支付
   - 周期性支付

3. **通知**
   - 状态变化时发送邮件或 webhook 通知
   - 失败告警

4. **报表/分析**
   - 每日交易量
   - 成功/失败率
   - 每笔支付平均处理时长
   - 图表可视化

5. **并发处理**
   - 两个用户同时更新同一支付会发生什么？
   - 实现乐观锁或悲观锁

6. **支付冲正/取消**
   - 在 COMPLETED 前取消支付
   - 冲正已完成支付（创建一笔新的对冲支付）

7. **多币种支持**
   - 汇率查询
   - 货币转换

8. **审计日志**
   - 跟踪每个操作由谁执行
   - 保留合规所需的详细日志

## 附录 F：测试考量

可考虑以下测试场景：

1. **Happy Path（主流程）**
   - 创建一笔支付，并观察其状态依次推进至 COMPLETED

2. **校验失败**
   - 尝试创建负金额支付
   - 尝试创建无效货币支付
   - 尝试创建源账户与目标账户相同的支付

3. **重复检测**
   - 使用相同幂等键提交同一笔支付两次
   - 验证第二次请求返回已存在支付

4. **非法状态迁移**
   - 尝试将 COMPLETED 支付回退到 CREATED
   - 验证返回合适的错误响应

5. **并发更新**
   - 两个请求同时尝试更新同一笔支付
   - 验证数据一致性

6. **数据库故障模拟**
   - 如果处理过程中数据库不可用会发生什么？
   - 状态更新是否应回滚？

## 附录 G：架构建议

可考虑采用分层架构：

```
┌─────────────────────────────────────┐
│         Web UI (Frontend)            │
│   (React, Vue, Angular, or similar)  │
└──────────────┬──────────────────────┘
               │ HTTP/REST
┌──────────────▼──────────────────────┐
│         REST API Layer               │
│    (Spring Boot / Flask / Express)   │
├──────────────────────────────────────┤
│         Business Logic Layer         │
│   - Payment validation               │
│   - Status transition logic          │
│   - Idempotency checking             │
├──────────────────────────────────────┤
│         Data Access Layer            │
│   - Repository pattern               │
│   - Transaction management           │
└──────────────┬──────────────────────┘
               │
┌──────────────▼──────────────────────┐
│         Database                     │
│   (PostgreSQL / MySQL / MongoDB)     │
└──────────────────────────────────────┘
```

**关键考量：**
* 将关注点拆分到清晰的层次
* 让业务逻辑可脱离数据库独立测试
* 数据访问可考虑使用 Repository 模式
* 使用依赖注入以降低组件耦合
* 为数据库操作实现合适的事务管理
